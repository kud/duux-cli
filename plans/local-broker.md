# Local broker — making the fan controllable

## Why

Duux's cloud refuses control for this account. Both endpoints answer HTTP 200
with `{"data":null,"errorMessage":"Not_Allowed"}`:

- `GET  v5/data/{id}/status`
- `POST v5/sensor/{id}/commands`

Discovery (`v5/sensor`) works, so `duux discover`, `devices`, `switch` and
`prefs` are fine. Only live state and commands are blocked.

Authenticating to Duux's own MQTT broker is not an option either: TLS succeeds
with the pinned certificate, but the CONNECT is rejected with
`Bad username or password`, and the credentials are not obtainable from the
REST API — no endpoint exposes them, and no combination of token, user id or
email is accepted.

**The fan is an MQTT client.** It dials out to `mqtts://collector3.cloudgarden.nl:443`.
So rather than getting permission from Duux, redirect that hostname to a broker
on your own network. The fan connects to you, publishes its state to you, and
takes commands from you. There is no third party left to refuse.

```
before:  duux-cli ──> Duux cloud ──> fan          (cloud can say no)
after:   duux-cli ──> your broker <── fan          (nobody can)
```

## Already done

Generated by the session of 2026-07-31, all under `~/.config/duux/broker/`:

| File             | What                                                              |
| ---------------- | ----------------------------------------------------------------- |
| `ca.crt`         | Self-signed cert, CN + SAN `collector3.cloudgarden.nl`, 10 years  |
| `broker.key`     | Its private key, mode 600                                         |
| `openssl.cnf`    | The config it was generated from, to regenerate if the IP changes |
| `mosquitto.conf` | Broker config — TLS on 443, `allow_anonymous true`                |

The certificate's SAN list includes `collector3.cloudgarden.nl`, `localhost`,
`127.0.0.1` and `192.168.1.103`. Cloudgarden's own certificate omits its
hostname, which is why `@kud/duux` has to bypass the hostname check for their
broker but not for yours.

Code support is shipped in `@kud/duux-cli`:

- `duux broker <host>` / `duux broker clear` — set or unset the local broker
- `src/lib/transport.ts` builds an MQTT transport from it, reading `ca.crt`
- `status`, `debug` and the TUI session all route through it when configured

## Steps remaining

### 1. Install and run the broker

```sh
brew install mosquitto
sudo mosquitto -c ~/.config/duux/broker/mosquitto.conf -v
```

`sudo` is needed only because 443 is a privileged port. The alternative is to
run on 8883 and redirect with `pf`, which also needs root once — simpler to
just bind 443.

To keep it running, `brew services` won't pick up a custom config path, so use
a launchd plist or a `tmux` pane while testing.

### 2. Give this machine a static LAN address

Currently `192.168.1.103`. Reserve it by DHCP on the router, otherwise the DNS
rewrite below breaks the next time the lease changes. If the address does
change, regenerate the certificate — the IP is in its SAN list:

```sh
cd ~/.config/duux/broker
# edit the IP in openssl.cnf first
openssl req -x509 -nodes -newkey rsa:2048 -days 3650 \
  -keyout broker.key -out ca.crt -config openssl.cnf
```

### 3. Redirect the hostname

On the router, Pi-hole, AdGuard, or whatever serves DNS to the fan:

```
collector3.cloudgarden.nl  →  192.168.1.103
```

This must apply to the **fan's** DNS, not just this Mac. If the fan uses a
hardcoded resolver, redirect port 53 at the router instead.

### 4. Power-cycle the fan

It only resolves the hostname on connect. Pull the plug, wait, plug it back in.
Watch the broker log — a successful `New client connected` from the fan's IP is
the moment this works.

### 5. Point the CLI at it

```sh
duux broker 192.168.1.103
duux status
```

## Verifying

The fan publishes to `sensor/{id}/in` and accepts commands on
`sensor/{id}/command`, both already implemented in `@kud/duux`. To watch raw
traffic while debugging:

```sh
mosquitto_sub -h 192.168.1.103 -p 443 --cafile ~/.config/duux/broker/ca.crt -t 'sensor/#' -v
```

Note the `{id}` in those topics is unverified — `@kud/duux` uses the numeric
sensor id (`373883`), but the fan may use its MAC (`28:05:a5:43:1f:c0`).
Subscribing to `sensor/#` above will show which, and it is a one-line change in
`src/transport/mqtt.ts` if it is the MAC.

## Open questions this unblocks

Once state flows, two things recorded as unverified can be settled:

- **Does the fan report `swing` as 0–3?** The command range is confirmed; that
  the reported field uses the same range is inferred. See `types.ts`.
- **Is `verosc` a toggle or a range like `horosc`?** No confirmation exists
  either way. `duux debug "tune set verosc 2"` will answer it.
- **Night mode readback.** `FanState` has no field for it. A real state payload
  will show whether the fan reports one.
